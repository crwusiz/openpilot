## 22초 재접속 지연

11:37:21 Pi는 JPEG 84095바이트 중 76728바이트를 받은 상태에서 전체 2초 제한을 넘겼다. 마지막 진행은 71ms 전이지만 진행 때마다 제한을 연장하지 않는 기존 정책에 따라 연결을 정리했다. C4도 같은 시각에 ACK EOF를 기록했다. 이때 TCP 진단은 lost=3, cwnd=16, 재전송 누계 750이었다.

Pi는 11:37:21.345에 저장된 C4 주소로 바로 연결했지만 6ms 뒤 reset을 받았다. 이후 서브넷 스캔을 반복하다 11:37:42.357에 연결했고 11:37:43.673에 스트리밍으로 복귀했다. C4는 11:37:21에 이미 LISTEN을 기록했으므로 연결 복구·주소 탐색 경로를 함께 보완할 근거가 있다. 이 구간에도 모델·위치 메시지는 신선했다.

두 가지 코드 문제를 보완했다.

1. 알려진 C4 주소에도 탐색용 120ms 접속 제한을 사용했다. 이번 정상 표본의 평균 TCP RTT도 약166ms이므로 너무 짧은 제한이다. 저장 주소와 명시적 `--host`에는 회당 최대1초·최대2회, 중간150ms를 포함해 총2초의 접속 예산을 적용한다. 대기 중에는 약50ms마다 SDL 이벤트를 처리한다. 실패 후에만 기존 주소 탐색으로 넘어가며 명시적 `--host`는 스캔하지 않는다. 주소가 바뀌었을 때의 탐색 fallback도 유지한다.
2. C4 sender의 복구 예외 경로가 `close()`로 listener까지 닫았다. Pi의 빠른 재접속이 이미 accept 큐에 들어와 있으면 이전 client 정리가 새 연결까지 reset할 수 있다. 복구용 `reset_connection()`은 이전 client·ACK reader·pending만 정리하고 listener는 유지한다. 최종 종료는 기존대로 listener와 포트를 닫는다. 이 경합은 로컬 TCP 회귀로 재현·검증했지만 이번 reset의 실제 원인 전체를 확정한 것은 아니다.

JPEG 완료 제한을 늘리거나, 22초가 반드시 2초로 줄어든다고 가정하지 않는다. 2초는 알려진 주소에 대한 접속 시도 예산이며 무선 장애·스캔·짧은 연결의 기존 backoff와 화면 준비 시간은 별도다.

## C4 합성 비용

렌더 경과 약48ms 중 실제 메인 스레드 CPU는 약30ms다. 나머지 약18ms에는 GIL·잠금·스케줄 대기 등이 포함되므로 전부 픽셀 계산 비용이나 OS 스케줄러 하나로 단정할 수 없다. CPU 우선순위와 네이티브 스레드 제한은 유지한다.

완전히 투명한 차선·도로 경계는 기존에도 화면에 영향을 주지 않았지만, 투명도를 확인하기 전에 3D 경계 배열과 투영 좌표를 만들었다. 확률≤0인 차선, 신뢰도≤0인 도로 경계는 투영 전에 생략한다. 확률의 새로운 문턱값을 도입하거나 유효한 선을 숨기지 않는다. 기존 픽셀 결과와 생략되는 투영 호출을 회귀로 비교한다. 다음 로그에는 `path_cpu_avg`도 추가해 경로 단계의 실제 CPU와 경과 시간을 구분한다.

## 주행 입력과 무선 상태

이번 207개 RESOURCE 창에서는 model lagging·commIssue가 모두0이고 주요 PID도 유지됐다. 모델 수신 age 최대87.8ms, motion67.2ms, 모델 실행 peak33.5ms였다. location 입력 오류9회와 부하 제한1.364초는 시작 직후에만 있었다. 어제의 긴 입력 중단이나 지속적인 5FPS 보호 제한으로 이번 낮은 FPS를 설명할 수 없다. 주행 이벤트·경고 조건은 변경하지 않는다.

Pi의 시작·설치 지문은 `b499b901...`로 일치하고 서비스 재시작0이다. 어제 Pi 코드 변경이 없었으므로 같은 지문은 정상이다. 수집 당시 주파수2447MHz·절전off였으며, `signal: 9dBm`은 드라이버의 비정상적인 양수 출력이므로 신호가 좋다는 근거로 사용하지 않는다. station 통계가 비어 있고 인터페이스 오류0만으로 무선 손실이 없다고 볼 수 없다. C4 재전송 증가량은 PERF 합1431, 종료 오류 표본까지 포함하면1450이다. TCP 세그먼트 수이며 JPEG 손실 프레임 수와 다르다.

다음 업로드에는 Pi 보고서 앞쪽에 C4의 Wi-Fi snapshot도 함께 넣는다. Pi 주소로 향하는 실제 route의 인터페이스를 선택하고 절전·주파수·신호·PHY 속도·재전송/실패 카운터를 숫자로 재출력한다. 인터페이스 통계도 읽으며 SSID·MAC·프로필·원본 명령 오류는 저장하지 않는다. AP의 station은 익명 최대2개이며 어느 항목이 Pi인지 단정하지 않는다. 로컬 수집 예산은 기존25초 안의 최대2초, 정제 metadata는 최대4 KiB, 전체 보고서는 기존512 KiB로 제한한다. 지원하지 않거나 명령이 실패해도 Pi 수집은 계속한다. 이는 업로드 시점의 상태이므로 주행 중 오류 순간을 직접 측정한 값은 아니다.

이번 수정은 C4와 Pi 양쪽에 있다. C4 코드를 업데이트하고 `bash scripts/pi_update.sh`로 Pi 수신기를 반영한다. 기존 wrapper는 정상 업데이트 뒤 Pi 재부팅을 예약한다. C4 cluster 프로세스도 재시작해야 한다. 다음 로그에서 알려진 주소 재시도·listener 유지, 실제 출력 FPS와 생성→ACK 나이, path CPU·JPEG 수신 대기와 재전송을 함께 비교한다. H.264/WebRTC로 전환할 경우 Pi의 실제 하드웨어 디코더와 카메라·HUD 분리 합성을 별도로 검증해야 하며, 이번 로그만으로 그 경로의 FPS를 보장하지 않는다.

로컬 검증은 C4 cluster 전체, 네트워크 전송·연결 수명, Pi 수신·빌드·TCP 진단과 수집기를 함께 실행해 646개가 통과했다. 실제 TCP로 새 접속을 listener에 대기시킨 뒤 이전 client만 정리해도 접속이 유지되는지 확인했다. 알려진 주소의 느린 handshake·일시 거부·총예산·종료/시간 초과와 경합한 소켓 정리, 투명 선의 픽셀 일치, CPU/경과 시간 집계, C4 snapshot 정제·시간/출력 상한도 검증했다. 변경한 Python 파일의 Ruff와 `git diff --check`가 통과했다. 실제 C4·Pi에서 새 코드로 주행한 결과는 아직 측정하지 않았다.
