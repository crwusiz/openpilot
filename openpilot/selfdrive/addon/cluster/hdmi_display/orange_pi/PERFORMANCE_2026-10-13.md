새 Pi 수신기는 반영됐다. 세 파일 모두 시작 소스 지문과 수집 시 설치 지문이 `b499b901...`로 일치하며 TCP_INFO와 주소 캐시 재접속 기록이 있다. 이전 주차장 로그의 구형 수신기 문제와 구분한다.

11:33 C4 파일의 289줄은 12:56 C4 파일의 동일한 prefix다. 이 부분은 중복 집계하지 않았다. Pi 현재 PID의 RX 기록이 있는 구간에 UTC+9를 적용해 C4와 대응시켰다. Pi 부팅 초기 벽시계는 보정된 흔적이 있으므로 journal의 큰 초기 시각 공백을 정지 시간으로 계산하지 않았다. 아래 값은 약 10초 통계 창들의 산술평균이다. 서로 다른 장면·통계 창 경계와 원본 촬영 시각의 차이가 있어 전체 프레임의 가중평균이나 카메라→HDMI 지연은 아니다.

화면 합성 평균이 20FPS의 50ms 예산을 초과한다. 동시에 전처리는 실제 출력보다 초당 약 4~5번 더 수행된다. 이 중복 변환은 매번 약 30ms이므로 줄일 가치가 있다. JPEG 디코딩이나 Pi 표시 큐만으로 낮은 FPS를 설명할 수 없고, C4 합성·전처리와 전송 대기 양쪽을 봐야 한다. 송수신·합성·인코딩은 겹쳐 수행되므로 단계 평균을 단순히 더해 FPS를 계산하지 않는다.

TCP 재전송은 계속 관측된다. 오전 Pi에는 11:32:13에 77495바이트 중 73848바이트까지 받은 뒤 2초 payload 제한을 넘긴 기록이 있다. 저녁 C4의 18:00:20 연결 종료에서는 재전송 누계 640·혼잡 창 1과 함께 오류가 있었고 같은 초에 새 연결이 시작됐다. 이는 늦은 JPEG와 링크 손실이 남았다는 증거지만 Wi-Fi 채널이나 특정 장치가 원인이라는 확정은 아니다. Pi의 station 통계가 비어 있어 인터페이스 errors/dropped=0을 무선 손실 부재로 해석하지 않았다. 소켓 버퍼와 시간 제한은 늘리지 않았다.

## 통신 경고와 모델 입력 중단

`events.py`의 `comm_issue_alert`는 실패한 SubMaster 서비스 이름을 표시한다. 발생 조건은 selfdrived의 `all_checks`, `all_alive`, `all_freq_ok`에 있다. 모델 drop이 2%를 넘는 `modeldLagging`과 다른 경고다. 첨부 로그에는 `commIssue`의 실제 실패 서비스 목록이 없으므로 사용자가 본 경고가 어느 서비스의 invalid/alive/frequency 문제였는지는 확정할 수 없다.

모델·위치 입력의 실제 중단은 있다. 12:56 C4 누적 로그에서:

- 11:43:18~11:44:38: 모델 입력 age 최대 40.65초, 해당 창의 클러스터 CPU 평균 35.2%.
- 11:54:30~12:17:53: 입력 age 최대 1361.15초(약 22.7분), 해당 141개 창의 클러스터 CPU 평균 7.7%. 대부분 Pi 연결이 없고 합성은 약 1FPS이며 차량 입력은 신선하다. 12:17:13 재수신과 모델 실행 peak 607ms 뒤에도 다시 입력 중단이 보이고 12:18:04에는 신선한 메시지로 돌아온다.
- 12:18:04~12:30:35: 76개 통계 창에서 deviceMotion `inputsOK=0`. 12:30:45에는 true로 복구한다. 모델 drop peak는 최대 0.5%이며 modeldLagging 임계치 초과 갱신은 세 파일 모두 0이다.
- 12:55:40~12:56:10: 모델·motion의 age가 다시 약 35초까지 증가한다.

model_lagging_updates=0은 모델 메시지가 계속 발행된다는 증거가 아니다. 메시지가 멈추면 마지막 drop 값도 고정된다. 반대로, 22분 이상의 중단 중 클러스터 작업량이 낮았다는 점은 단순한 지속적 클러스터 CPU 포화와 맞지 않는다. 시작 순간의 자원 경쟁·GPU 정체·모델 로딩·프로세스 장애 중 어느 원인인지는 manager/modeld/locationd 원로그가 필요하다. 이번 자료로 클러스터가 원인 또는 무관하다고 확정하지 않는다.

## 적용한 수정

1. 카메라가 아직 소비하지 않은 전처리 영상을 다시 변환하던 작업을 줄였다. 원본은 계속 받아 비우며, 대기 중 약 5Hz 갱신과 전송 여유 복귀 시 즉시 변환을 유지한다.
2. 경로·차선 합성은 렌더러별 단색 띠·출력 버퍼를 재사용한 addWeighted로 변경했다. 그라데이션과 픽셀 결과는 기존 OpenCV 합성과 동일하게 검증했다. 12색 캐시와 출력 버퍼는 기본 Network 크기에서 약 3 MiB로 제한된다.
3. 주행 입력 age가 500ms를 넘거나 location 입력 검증 실패·주행 통신/프로세스 경고가 있으면 보조 화면 합성·인코딩을 최대 5FPS로 제한한다. 1초간 정상 상태가 유지되면 원래 목표로 복구한다. 카메라 원본 수신과 HUD 입력 갱신은 계속한다. 경고 판정이나 주행 프로세스를 수정하지 않는다.
4. 실제 selfdriveState 경고, errorLogMessage의 commIssue 실패 서비스 목록, manager의 주요 PID·실행 상태·종료 코드 변화를 C4 로그에 남긴다. 읽기 전용 구독이고 pending 진단은 최대 16개다. 모든 원로그를 보존하는 수집기는 아니므로 오류가 연속 발생하면 일부 errorLogMessage가 생략될 수 있다.

Windows PC/OpenCV 5.0의 단일 스레드 비교에서 4차선·2도로 가장자리·그라데이션 합성은 기존 1.642ms→재사용 경로 1.261ms로 약 23% 감소했다. RGB 띠 합성만 비교하면 2.5~2.7배 빨랐지만 전체 합성에는 마스크·투영·HUD 비용이 남는다. 이는 C4 ARM에서 측정한 성능이나 주행 20FPS 달성을 뜻하지 않는다. 실제 개선과 경고의 발생 원인은 새 로그에서 확인해야 한다. 기본 JPEG 품질 68·정상 목표 20FPS는 유지한다.
