## 낮은 FPS의 원인 범위

어제 적용한 미소비 카메라 영상의 중복 전처리 제한은 동작한다. 전처리는 약 11~12FPS에서 6.8~7.2FPS로 줄었고 원본은 약 20FPS로 계속 수신한다. 다만 실제 표시 FPS는 약 6.5~6.9에 머문다.

주행 입력 부하 제한이 활성화된 시간은 각 구간에서 64초(3.06%), 15초(0.45%), 5초(0.10%)다. 제한이 없는 창의 FPS도 약 7.08 / 6.49 / 6.64라서 5FPS 보호 제한이 지속적인 낮은 FPS의 주원인은 아니다. 경로가 없는 오후 창에서도 합성은 약 21ms로 줄지만 출력은 약 6.6~6.7FPS다. 합성 최적화만으로 전송 대기를 해결할 수는 없다.

코드에서 전송 창이 가득 차면 다음 화면의 합성까지 금지하는 대기를 확인했다. ACK가 한 슬롯을 비운 다음에야 메인 루프가 새 화면을 합성하고 JPEG를 인코딩하므로, 빠져나간 슬롯을 다시 채우는 동안 작업이 직렬로 이어진다. 건강한 연결에서 다음 JPEG 한 장을 미리 준비하면 이 부분을 겹쳐 실행할 수 있다. 단, 경로가 있는 합성 시간도 20FPS의 50ms 예산을 넘으므로 HUD와 경로 비용은 계속 확인해야 한다.

TCP 재전송도 남아 있다. 마지막 C4 누적 파일의 PERF 표본에서 `tcp_retrans_delta` 합계는 22969다. 이는 표본 구간의 TCP 세그먼트 재전송 증가량이며 JPEG 손실 프레임 수나 모든 연결의 정확한 총 재전송 수는 아니다. 같은 파일에 네트워크 오류 12건과 파이프라인 오류 7건이 있다. ACK 대기가 긴데 C4 `send_avg`가 짧다고 링크가 충분히 빠르다고 해석하지 않는다.

Pi 수집 시 Wi-Fi는 2.4GHz 2417MHz, 절전 off, PHY 86.7Mbps였다. station 통계는 비어 있어 인터페이스 errors/dropped=0으로 무선 손실이 없다고 판단할 수 없다. PHY 수치는 JPEG 실효 처리량과 다르다. 재전송·RTT·본문 수신 시간 때문에 이번 코드 보완만으로 실제 20FPS를 보장하지 않는다.

## 주행 통신 경고

이번 누적 파일에는 `commIssue` 오류 진단 87개와 실제 selfdriveState의 통신 경고 시작 11회가 있다. 하지만 raw 진단의 `not_alive` 목록에 반복되는 `alertDebug`, `lateralManeuverPlan`은 selfdrived의 alive/frequency/valid 검사에서 제외하는 서비스다. GPS와 센서도 같은 제외 설정이 있으므로 raw 목록을 경고의 실제 원인 목록으로 그대로 해석하면 안 된다.

제외 항목을 빼면 `invalid`에서 extrinsicsCalibration, vehicleParameters, longitudinalPlan, driverAssistance, lateralDelay, lateralTorqueParameters가 관측된다. 이 자료로 각 발행 프로세스가 invalid를 보낸 이유나 cluster와의 인과관계까지 확정할 수는 없다. modelV2와 deviceMotion은 해당 실패 목록에 없으며, 이번 파일의 모델 수신 age 최대는 126.5ms, motion은 129.9ms, 모델 실행 peak는 33.9ms, model lagging 업데이트는 0이다. 어제의 수십 초~22분 입력 중단은 이번 파일에서 관측되지 않았다. 주행 경고 조건과 제어 프로세스는 변경하지 않는다.

## 적용한 수정과 다음 비교

1. 정상 스트리밍 연결에서는 전송 창이 찼더라도 다음 JPEG 한 장을 미리 준비한다. 실제 전송의 기본 2장 / 512 KiB 예산을 유지한다. 기존과 같이 JPEG 한 장 자체가 512 KiB보다 클 때는 대기 ACK가 없는 경우만 예외로 허용한다. ACK가 250ms를 넘게 기다리거나 연결 오류가 있으면 미리 준비도 중단한다. 생성 후 250ms를 넘긴 대기 프레임은 계속 폐기한다. 전송 대기 중 추가 렌더·인코딩을 반복하지 않는다.
2. 헤더와 JPEG를 한 번의 `sendall`로 보낸다. TCP_NODELAY에서 작은 헤더를 먼저 별도 쓰던 호출을 합쳤으며 프로토콜 바이트와 Pi 수신기는 동일하다. 이것만으로 재전송이나 Wi-Fi 지연이 사라진다고 가정하지 않는다.
3. HUD 숫자의 글자 모양을 색과 분리해 캐시한다. 가감속에 따라 속도 색이 변해도 같은 숫자와 글꼴의 마스크를 재사용한다. 기존 픽셀·외곽선·투명도·정렬은 회귀 비교로 확인하며 캐시는 최대 256개 / 8 MiB로 제한한다.
4. `[CLUSTER_MAIN_PERF] render_cpu_avg`를 추가한다. 기존 `render_avg`는 합성 중의 잠금·GIL·OS 스케줄 대기를 포함하지만 새 항목은 렌더 메인 스레드가 실제 실행된 CPU 시간이다. 단일 스레드 OpenCV 설정을 유지하며 프로세스 전체 CPU나 다른 스레드의 전처리·인코딩 시간과 구분한다.

기본 정상 목표 20FPS와 JPEG 품질 68을 유지한다. 우선 이번 수정 후 ACK 해제→새 전송의 대기, `encoded_wait_avg`·`send_age_avg`, 실제 `display_fps`·`display_gap_max`, HUD 시간과 render CPU 시간을 비교한다. FPS가 올라가도 생성→ACK 나이가 늘면 성공으로 판단하지 않는다. 링크 지연·재전송이 계속 지배적이면 하드웨어 H.264/WebRTC와 Pi의 실제 디코더 지원을 확인하는 별도 경로가 필요하다. 이는 Pi에서 카메라·HUD를 따로 합성하는 설계 검증을 포함하며 단순 프로토콜 변경으로 처리하지 않는다.

이번 변경은 C4 코드에 있다. 실행 중인 C4 cluster 프로세스를 재시작해야 적용되며 Pi 수신기는 현재 버전과 호환된다. 실제 장비에서 변경 후 성능을 측정하기 전에는 향상 FPS를 확정할 수 없다.

로컬 검증은 C4 cluster 전체 테스트, 네트워크 송신·연결 수명, Pi 수신·TCP 진단을 함께 실행해 583개가 통과했다. 글자 변경은 이전 픽셀과의 일치, 색상 변경 시 재래스터화 생략, fallback 글꼴·외곽선·투명도·잘림과 메모리 상한을 검증했다. 전송 변경은 한 번의 쓰기에서 동일한 wire 바이트, 슬롯 대기 중 준비 한 장, 만료 폐기와 연결 오류 정리를 검증했다. 변경한 Python 파일의 Ruff와 `git diff --check`도 통과했다.
