# 2026-10-16 Network cluster 비교와 보완

두 모드를 유지한다. H.264를 우선 개선하며 JPEG는 비교·복구용으로 둔다. H.264의 표시 FPS와 C4 메모리는 유리하지만, Pi 자산 접근 오류와 디코딩·연결 오류가 남아 있어 JPEG를 제거할 근거는 부족하다. 저장된 코덱 선택은 강제로 바꾸지 않는다.

## 로그 비교

15:25·15:29·15:37 업로드는 같은 15:19 H.264 세션의 누적 로그다. 중복을 제외하고 15:37 사본과 16:55 JPEG 사본을 비교했다. Pi journal은 UTC이므로 아래 시각은 9시간을 더한 KST다.

| 구간 | Pi 표시 FPS | 모델 입력이 있는 구간의 C4 CPU / RSS |
| --- | --- | --- |
| JPEG 16:19–16:55 | 약 7.25 | 약 53.7% / 160.5 MB |
| H.264 15:19–15:37 | 약 15.03 | 약 42.9% / 61.8 MB |

H.264는 C4 영상 전송 20.00 FPS, Pi 디코딩 후 수신 약18.63 FPS였다. Pi 합성 약24.7ms, 표시 처리 약14.4ms이며 수신·표시 사이의 대기와 불규칙한 도착도 FPS에 영향을 준다. JPEG는 ACK 평균 대기 약226.8ms, 렌더 약28.2ms, JPEG 준비 약26.2ms로 전송 대기가 주요 제한이었다. 서로 다른 주행 구간이므로 같은 조건의 실험 결과로 간주하지 않는다.

두 세션에서 model lagging·comm issue 누적은 0이었다. 각각 시작 중 잠깐의 motion input 보호가 있었으며, 이 기록만으로 다른 주행 프로세스와의 인과관계를 증명하지 않는다.

## 확인한 문제와 수정

- Pi 서비스 시작 기록은 폰트 2개·아이콘 27개 모두 읽기 실패인데, root 계정의 업로드 시점 검사는 같은 자산을 읽었다. `Failed to load fonts: cannot open resource`도 반복됐다. 서비스 계정의 디렉터리 접근 권한이 강하게 의심된다. 업데이트·설치에서 기존 `assets` 상위 폴더까지 755, 자산 파일은 644로 복구한다. H.264는 작은 기본 글꼴이나 빈 아이콘으로 조용히 진행하지 않고 실패 경로를 명시한다. 정상 폰트 크기와 레이아웃은 JPEG와 같다.
- Pi의 고정 20ms 대기가 렌더 기한을 지나치고 표시 주기를 밀 수 있었다. 다음 표시 기한까지 기다리고, 처리 지연 시 지난 슬롯을 건너뛰도록 수정했다. 결정적 시계 검증은 실제 장비 FPS를 대신하지 않는다.
- H.264 디코딩 오류가 첫 세션 220회, 다음 세션 523회 기록됐다. RTCP 손실은 순간 최대12.11%였다. 디코더 오류·영상 정체 시 복구 요청을 보내고, C4는 최대2초 간격으로 키프레임을 요청하며 새 IDR 전까지 참조가 불완전한 프레임을 보내지 않는다.
- 상태 메시지의 경로·HUD 실수는 소수점 3자리, 보정 행렬은 6자리로 전송한다. 카메라 영상 인코딩은 바꾸지 않는다. 페이로드 감소와 투영 오차가 1픽셀 미만임을 테스트한다.
- 오전 `08:20:55 CLUSTER_DEPS_WAIT`에서 `08:38:50 READY`까지는 의존성의 오프로드 준비 대기였다. 제공 로그에는 실제 C4 시작 실패의 예외·종료 진단이 없다. 시작 단계 Python 예외와 native 오류를 `cluster_crash.log` 및 회전 파일에 보관하고, 최근 오류를 다음 세션과 Pi 업로드 진단에 포함한다. Pi 서비스 계정·자산 폴더 권한·서비스 계정으로 읽은 자산 지문도 수집한다.

## 적용 후 검증

C4 코드를 업데이트하고 `bash scripts/pi_update.sh`로 Pi도 갱신·재부팅한다. 먼저 H.264에서 JPEG와 같은 크기의 폰트와 모든 아이콘이 나오는지 확인한다. 정상 자산이 추가된 뒤에는 합성 비용이 달라질 수 있으므로 표시 FPS와 최대 표시 간격을 다시 측정한다.

다음 로그에서는 `[CLUSTER_H264_RX_PERF]`의 표시 FPS·디코더 오류, `[CLUSTER_H264_RECOVERY]`, C4 CPU·입력 보호 상태를 함께 본다. 연결 실패나 프로세스 종료가 있으면 같은 방식으로 C4·Pi 로그를 업로드한다. 복구 로그는 원래 세션보다 오래된 기록일 수 있어 기록된 시각과 함께 해석한다.
