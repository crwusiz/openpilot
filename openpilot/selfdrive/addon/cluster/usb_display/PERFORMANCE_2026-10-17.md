# USB H.264 기기 로그 확인

대상은 `26-10-17-15_37_Unknown_UnregisteredDevice_cluster_debug.log`와
`26-10-17-15_47_Unknown_UnregisteredDevice_cluster_debug.log`입니다.
아래 수치는 시작 구간을 포함한 각 10초 통계 행의 산술 평균입니다.

| 항목 | 15_37 로그 | 15_47 로그 |
| --- | --- | --- |
| USB 제출 FPS 평균 | 13.56 | 13.34 |
| USB 제출 FPS 범위 | 11.62~14.47 | 11.49~13.87 |
| 제출 통계 표본 수 | 13 | 14 |
| RGB→NV12 변환 평균 | 55.85ms | 57.99ms |
| 변환 통계 표본 수 | 14 | 15 |
| heartbeat에서 관측한 전송 실패 | 0 | 0 |
| 모니터가 보고한 큐 깊이 | 0 | 0 |

사용자가 USB에서도 부드러운 출력을 확인했습니다. 로그에는 하드웨어 인코더 오류나
Python crash 기록이 없고, 지속적인 USB 전송 큐 적체도 보이지 않습니다.
다만 `submitted_fps`는 USB 전송 완료 횟수이며 모니터의 실제 표시 FPS가 아닙니다.

목표 20FPS의 프레임 간격은 50ms입니다. 현재 직렬 RGB→NV12 변환만 평균 약56~58ms를
사용하므로 이 경로가 목표 속도를 제한합니다. 합성·변환·하드웨어 출력 준비·USB 전송은
겹쳐 실행되며, `prepare_avg`에는 비동기 출력 대기도 포함되므로 이를 순수 하드웨어
인코딩 시간으로 해석하거나 단계 시간을 단순 합산하지 않습니다.

차량·모델 입력이 관측되지 않은 구간이므로 이 두 로그만으로 실제 주행 시 modeld나
locationd에 미치는 영향을 판단할 수 없습니다. 이후 검증에서는 변환 시간과 제출 FPS에
더해 `[CLUSTER_INPUT_DIAG]`, `[CLUSTER_RESOURCE_PERF]`, 부하 보호 기록을 함께 확인합니다.

이후 USB·Network H.264 전용 실행 경로를 적용한 결과는 다음 절에 기록합니다.

## H.264 전용 적용 후 16_17 로그

대상은 `26-10-17-16_17_Unknown_UnregisteredDevice_cluster_debug.log`입니다.
시작·전체 카메라 프로세스 재시작이 포함된 첫 두 통계 행을 제외한 20개 표본 기준입니다.

| 항목 | 평균 |
| --- | --- |
| USB 제출 FPS | 12.21 (11.73~12.89) |
| RGB→NV12 변환 경과 시간 | 63.62ms |
| 원본 카메라 수신 | 20.00FPS |
| 새 RGB 카메라 영상 준비 | 7.41FPS |

전체 22개 전송 통계의 USB 쓰기는 평균13.90ms이고 큐 깊이는 모두0입니다.
전송 실패·인코더 오류·프로세스 crash는 기록되지 않았습니다. 시작 중16:13:29~32의
카메라 stale/reconnect는 manager가 카메라·모델 등 전체 주행 프로세스를 중지하고
새 PID로 시작한 구간과 겹칩니다. 이 기록만으로 재시작의 근본 원인은 판정하지 않습니다.

렌더링은 약12FPS여도 새 카메라 영상은 약7FPS였습니다. 짧게 열리는 인코딩·USB 준비
시점을 카메라 수신 시점에서 함께 요구해, 영상 준비가 최소 갱신 주기에 가까워지는
구조를 확인했습니다. 이제 렌더러가 영상을 소비하면 최신 한 장을 미리 준비합니다.
미소비 영상은 한 장만 보관하며, 연결 해제·부하 보호와 유휴5Hz 갱신은 유지합니다.

RGB 회전·패딩·BT.601 변환·UV 재배열은 기존 C4 인코더 공유 라이브러리의
`cluster_h264_encoder_bridge_convert_rgb`에서 한 번에 처리합니다. 고정 NV12 버퍼를
재사용하며 새 패키지나 변환 작업 스레드를 추가하지 않습니다. 상·하·좌·우 복제 패딩과
회전 후 색차 샘플 위치를 포함해 기존 OpenCV 결과와 바이트 단위로 비교합니다.
계수와 샘플 기준은 [OpenCV 구현](https://github.com/opencv/opencv/blob/5.x/modules/imgproc/src/color_yuv.simd.hpp)을 참고했습니다.

PC의 단일 OpenCV 스레드·1920×462 RGB 영상에서 변환 중앙값은 기존3.61ms,
네이티브2.55ms였습니다. C4의 CPU·스케줄링 환경이 다르므로 이를 기기 FPS로 환산하지
않습니다. C4용 라이브러리를 재빌드하고 `converter=native_tiled`인지 확인한 뒤 새 로그로
제출 FPS와 새 카메라 준비 FPS를 함께 비교합니다.

새 성능 로그의 `convert_avg`는 변환 전체 경과 시간, `convert_cpu_avg`는 해당 스레드가
실제로 CPU를 사용한 시간, `rgb_export_avg`는 PIL/NumPy 입력 준비, `pixels_avg`는
그 뒤 픽셀 변환의 경과 시간입니다. CPU 시간과 경과 시간의 차이가 크면 계산 외의
스케줄링·대기 영향도 함께 점검합니다. 비동기 출력의 지표는 각 입력 PTS에 보관하므로
다음 입력의 변환 시간을 이전 출력에 붙이지 않습니다.

차량·모델 입력은 이 로그에서도 관측되지 않았습니다. 실제 주행의 모델·위치 처리에
대한 영향과 이번 변경 후 기기 FPS는 이후 기기 로그에서 확인해야 합니다.
